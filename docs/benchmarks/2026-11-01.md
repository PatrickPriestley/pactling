# Benchmarks, 2026-11-01 (issue #6)

`scripts/bench.py` seeds a dataset over HTTP (aborting if any seed write fails), measures
the read paths with an otherwise idle broker, then runs mixed concurrent traffic for 30 s:
publish, verify, record-deployment and can-i-deploy in equal shares. A verify operation
is two HTTP requests (fetch the pact, publish the result). Throughput is per measured
second. The script runs unchanged against pactling and the Ruby broker.

**Hardware:** Apple M1 Pro, 16 GB, macOS 15.6.1. pactling release build with a SQLite file
in WAL mode; Ruby broker 2.121.2 in Docker Desktop with Postgres 12. Client on the same
machine. "Before" is `main` at the time; "after" is this branch.

## Datasets

| | Consumers | Providers | Versions each | Pact publications | Verifications |
|---|---|---|---|---|---|
| medium | 20 | 5 | 50 | 5,000 | 300 |
| large | 50 | 10 | 200 | 100,000 | 1,500 |

Each provider's newest version is deployed to the environment and tagged `prod`; the
previous one is released there. Each consumer's newest version is deployed as two
application instances.

## Findings

- **Two reads grew with publications times versions.** Every "latest pact per consumer"
  query used a correlated `MAX` subquery evaluated per publication (`EXPLAIN QUERY PLAN`:
  a correlated scalar subquery per scanned row). On the large dataset `/pacts/latest`
  took 28 s and pacts-for-verification with the default selectors 6.2 s. This branch
  computes the latest version per consumer once with `GROUP BY`; they now take 67 ms and
  25 ms, with identical results (every fixture test passes). `tests/performance.rs` holds
  a 1 s budget on 40,000 publications that the old queries miss by 4 to 8 times.
- **Everything else scales acceptably.** can-i-deploy stays under 40 ms p95 on the large
  dataset; the matrix for one integration across 200 versions is about 70 ms.
- **Writes serialise without errors.** No operation failed under contention in any run,
  and throughput is the same on both builds. Publish latency is dominated by waiting for
  the write lock (`BEGIN IMMEDIATE`, 5 s busy timeout). An earlier pair of runs showed
  publish p95 about 20% higher after the change; these runs do not, and the change touches
  no write path.
- **Against the Ruby broker** on the medium dataset, pactling answers reads 2 to 18 times
  faster and sustains about 15 times the mixed throughput on the same machine. The Ruby
  broker ran in Docker with Postgres, so this compares deployments as people run them,
  not engines.
- **Correctness:** the comparison shows a verdict difference. For consumer to environment
  pactling returns 10 rows and "not deployable" where the Ruby broker returns 5 rows and
  "deployable": pactling ignores `latestby`, so the released provider version, which
  failed its verification, is counted next to the deployed one (issue #23).

## Proposed targets

At the large size on this class of hardware: can-i-deploy p95 under 100 ms; every list or
selector read under 250 ms p95; zero errors under the mixed load; no read whose cost grows
with publications times versions. All are met after this branch.

## Not done

No cache was added and none is needed at these sizes. Query count per request was not
instrumented. Pool size, journal mode and busy timeout were judged only by the zero-error
result; none needed changing.

## Reproduce

```bash
cargo build --release
PACTLING_DATABASE_URL='sqlite:///tmp/bench.db?mode=rwc' PACT_BROKER_PORT=9393 target/release/pactling &
scripts/bench.py http://127.0.0.1:9393 --consumers 50 --providers 10 --versions 200 --rounds 10 --seconds 30 --out large.json
```
