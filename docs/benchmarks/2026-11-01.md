# Benchmarks, 2026-11-01 (issue #6)

`scripts/bench.py` seeds a dataset over HTTP, measures the read paths with an otherwise
idle broker, then runs mixed concurrent traffic (publish, verify, record-deployment and
can-i-deploy in equal shares). It runs unchanged against pactling and the Ruby broker.

**Hardware:** Apple M1 Pro, 16 GB, macOS 15.6.1, release build, SQLite file database in
WAL mode, client on the same machine. Ruby broker 2.121.2 in Docker Desktop with Postgres.

## Findings

- **Two reads grew with publications times versions.** Every "latest pact per consumer"
  query used a correlated `MAX` subquery evaluated per publication. On the large dataset
  `/pacts/latest` took 28 s and pacts-for-verification with the default selectors 6.3 s.
  This branch computes the latest version per consumer once with `GROUP BY`; they now take
  68 ms and 25 ms. `tests/performance.rs` holds a 1 s budget on 40,000 publications that
  the old queries miss by 4 to 8 times.
- **Everything else scales acceptably.** can-i-deploy stays under 40 ms p95 on the large
  dataset; the matrix for one integration with 200 versions is about 65 ms.
- **Writes serialise without errors.** No request failed under contention in any run.
  Publish p95 is dominated by waiting for the write lock (`BEGIN IMMEDIATE`, 5 s busy
  timeout); the worst single publish on the large dataset was about 2 to 3 s. Throughput
  is the same on both builds (about 88 requests/s). Publish p95 is about 20% higher after
  the change in both large runs; the change touches no write path, and it is recorded here
  rather than explained.
- **Against the Ruby broker** on the medium dataset, pactling answers reads 2 to 17 times
  faster and sustains about 17 times the mixed throughput on the same machine. The Ruby
  broker ran in Docker with Postgres, so this compares deployments as people run them,
  not engines.
- **Correctness:** the comparison exposed that pactling ignores `latestby`, so an
  environment holding a deployed and a released provider version yields two rows where
  the Ruby broker yields one (issue #23).

## Targets

The issue asks for agreed targets. Proposed, from these numbers: can-i-deploy p95 under
100 ms and every list or selector read under 250 ms at the large size on this class of
hardware, zero errors under the mixed load, and no read whose cost grows with
publications times versions. All are met after this branch.

## Not done

No cache was added and none is needed at these sizes. Query count per request was not
instrumented; the plans of the two slow queries were inspected with `EXPLAIN QUERY PLAN`
(a correlated scalar subquery per scanned publication). Connection, journal and busy
timeout settings were evaluated only as far as the zero-error result; a larger pool or
a longer timeout was not needed.

## Reproduce

```bash
cargo build --release
PACTLING_DATABASE_URL='sqlite:///tmp/bench.db?mode=rwc' PACT_BROKER_PORT=9393 target/release/pactling &
scripts/bench.py http://127.0.0.1:9393 --consumers 50 --providers 10 --versions 200 --seconds 30 --out large.json
```
